# Grok 机器人为什么烧钱：Harness 学习笔记

## 问题出在哪：一个机器人干所有事 <!-- toc: 问题出在哪 -->

<!-- lead -->
很多人的用法是：只开一个 Grok 机器人，让它写东西、选路线、做判断、批申请、还直接跑命令。这样有三个毛病：

1. **慢**：每一步都要等大模型用自然语言想一遍。
2. **贵**：很多步骤根本不是在写作，而是在做一个小决定，却也要按大模型的价格付费，还带着巨大的上下文。
3. **乱**：没有边界，半夜三点也可能自己干出奇怪的事。

作者举了一个例子：2026 年 7 月，Cursor 把一份 835 页的新编程语言规范交给一群 Agent，16 天后拿回了一个能用的编译器，中间没有人碰过代码。这说明问题不在模型本身，而在外面的组织方式。

这就引出我们之前聊过的那句话：**Agent = 模型 + Harness**。模型一样，Harness 不同，出来的 Agent 就完全不同。

## 四层分工：各干各的 <!-- toc: 四层分工 -->

作者的方案是把工作拆成四层：

- LAYER 01 · WRITES
  **Grok 负责写**：写代码、写草稿、做规划，这是它最擅长的事。
- LAYER 02 · DECIDES
  **Jev 负责决定**：选哪个、打几分、行不行，只做判断，不写长文。
- LAYER 03 · ENFORCES
  **Harness 负责管规矩**：定流程、卡边界、留记录。
- LAYER 04 · SCALES
  **Swarm 负责扩展**：人手不够时加人，而不是让一个人加班。

![图 1 · 四层 Agent 结构：请求从上进，交付从下出](kbimg:02-layers.jpg)

这个分法的好处是：贵的模型只留在真正需要它动脑的地方，小决定不再按大模型的价格结算。

## Harness 到底是什么 <!-- toc: Harness 是什么 -->

Harness 不是模型，而是模型外面那一圈东西：让它循环跑起来的流程、它能碰的工具、它不能破的规则、它留下的文件。作者认为一个能用的 Harness 要有六个零件：

1. **一个只管分派的主管**：负责接需求、拆任务、盯进度，自己不动手执行。
2. **每个机器人一份职责说明**：写清楚它负责什么结果、能信哪些来源、用什么标准判断好坏、最后交什么文件、绝对不能碰什么。
3. **一个共享工作区**：用文件而不是聊天记录来传活，这样换人、换机器人，上下文也不会丢。能长期留的文件放工作区，临时的放临时目录。
4. **三道检查**：来源、证据、行动，第 8 节会细说。
5. **每次任务结束留一份交接单**：做了什么、改了哪些文件、有什么证据证明、还剩什么、谁负责。
6. **一本你自己掌控的行动账本**：所有落地的操作都记下来，方便回头查。

![图 2 · PART 1 配图](kbimg:03-part1.jpg)

主管的工作方式大概是这样：收到需求先分类，再选对口的专业机器人，把任务写成文件交给它，等它交回交接单，再把成果汇总成三行摘要给你。只有涉及钱、发布、删除、签名这类不可逆的事，才直接找你。

## 最烧钱的地方：决策层 <!-- toc: 最烧钱的决策层 -->

<!-- lead -->
这是全文最关键的发现：Agent 循环里的大多数步骤，其实不是在写东西，而是在做决定。

比如：该读哪几个文件？该用便宜模型还是贵模型？这条命令安不安全？做完了吗？这段工具输出要留还是扔？以前这些决定都交给同一个贵模型，用自然语言回答，带着全量上下文，价格自然高。

Jev 是 Typesafe AI 的一个专用决策模型，思路完全不同：你把当前状态和几个结构化问题发过去，它直接返回结构化答案，不写散文。问题基本就三种：

- **选一个**：分给哪个组、走哪条路线、用哪个档位。
- **打个分**：按质量、风险、紧急程度给 1 到 5 分。
- **是或否**：返回 0 到 1 的概率，比如「能安全发送吗」，0.12 就表示大概率不行。

价格和速度，原文给的数字是：输入每百万 token **0.042 美元**，输出免费，端到端延迟 **70 到 500 毫秒**。

```bill
算一笔账：一次路由决定
输入 2,000 token、输出 150 token
Grok 4.7|$0.0049|输入 $2 / 百万 · 输出 $6 / 百万
58×
Jev|$0.000084|输入 $0.042 / 百万 · 输出免费
每天 1 万次这样的决定：约 $49 对 $0.84
```

作者建议先把五类决定挪过去：**选文件、选模型、判断能不能跑、判断做没做完、判断工具输出留不留**。做法是给 Grok 机器人加一条新习惯：凡是遇到选、评分、是或否，先问 Jev，按结构化答案行动；只有 Jev 没把握、或者决定不可逆时，才升级回 Grok 4.7。

这和我们之前说的 Harness 思路是一致的：大模型动嘴做判断，Harness 负责把判断变成一次便宜、结构化的调用，再把结果传回去。

## Swarm 怎么组才不乱 <!-- toc: Swarm 组队规则 -->

Swarm 不是机器人越多越好，拓扑其实很简单：一个主管，几个专业小组，共用一条总线和一个工作区。SpaceX AI 的人也是这么描述他们自己的系统的。作者给了五条组队规则：

1. **按瓶颈招人，不按应用招人**：不要搞「邮箱机器人」「浏览器机器人」，要看哪里卡住了，再补一个专门解决那个瓶颈的机器人。
2. **先从主管加一个专家开始**：只有活真的排队等了，才加下一个。
3. **小组之间用文件加一个线程沟通**：不要拉长聊天，任务和结果都落在工作区里。
4. **写代码交给隔离环境的云端 Agent**：Grok 机器人只负责把关结果，不直接在本地乱改。
5. **最后由一个中立的合并机器人统一落地**：它不写功能，只检查交接单在不在、测试过没过、有没有不可逆操作混进来，通过了才合入，缺东西就打回去，并把每次落地记到行动账本里。

![图 5 · PART 3 配图](kbimg:06-part3.jpg)

一个账号最多可以有 50 个机器人加群聊，作者的意思是：你根本用不了那么多，先少后多。

## 全栈对照：谁干什么、跑在哪、花多少钱 <!-- toc: 全栈对照表 -->

| 层 | 干什么 | 跑在什么上 | 花你什么 |
|---|---|---|---|
| Grok | 写代码、写草稿、做规划 | Grok 4.7 | 输入 $2 / 百万，输出 $6 / 百万 |
| Jev | 路由、打分、说是或否 | Jev 1.13.0 | 输入 $0.042 / 百万，输出免费 |
| Harness | 职责说明、检查、交接、记账 | 工作区 + 技能 | 你一次性的搭建时间 |
| Swarm | 并行的专家小组 + 合并 | Grok 机器人 + 云端代码 Agent | 机器人越多 token 越多，所以要慢慢加 |

> 贵的模型还在环里，只是不再为每一个小决定付费了。

## 三个例子：这套东西落到具体活上是什么样 <!-- toc: 三个落地例子 -->

### 例子 1 · 邮箱分流 —— 最适合先做的 Swarm

1. 收件机器人每小时读一次新邮件。
2. 每封邮件问 Jev 三个问题：分给哪个组、紧急程度 1 到 5 分、要不要先找人再动手。
3. 只有紧急程度不高、且「需要人」的概率很低时，才由回复机器人起草回复。
4. 其余的都连同草稿一起放进待审批区。
5. 主管每天 9 点和 17 点各给你发一次汇总。

这个例子好在：判断全是结构化的，风险可控，而且省下的全是重复劳动。

![图 7 · PART 5 配图](kbimg:08-part5.jpg)

### 例子 2 · 内容生产线

- 研究机器人只负责把可信来源收集到研究目录。
- 写作机器人只能根据这些来源写，不能自己编。
- 每篇草稿都交给 Jev，从清晰度、证据、钩子三个维度打分。
- 低于 4 分的打回一次，并指明最弱的一项和一个改法。
- 两次不过就连同分数一起交给你，永远不自动发布。

关键点是：质量判断也结构化了，改稿有明确依据，而不是「感觉不好，重写一遍」。

### 例子 3 · 代码小组

- Grok 机器人当技术负责人，先把工单拆成能单独测试的小单元。
- 每个单元派一个云端代码 Agent，范围、验收标准、不做什么是先写好的，两个 Agent 不碰同一批文件。
- 每个 Agent 跑命令之前，先问 Jev：这条命令会不会删东西、覆盖数据？概率超过阈值就停下来问你。
- 合并机器人负责合入，你只批不可逆的操作。

这个例子把「快」和「稳」分开了：并行是快，检查是稳。

## 上第二个机器人之前，先过一遍清单 <!-- toc: 上线前检查清单 -->

- 主管先存在，专家后加。
- 每个机器人都有五项职责说明。
- 工作区里有研究、草稿、证据、审批、交接这几类目录。
- 决定走 Jev，写作走 Grok。
- 每个对外动作都有三道检查。
- 只有一个合并机器人、一本行动账本。
- 默认安静，只在出异常时通知你。

### 三道检查，具体是哪三道

- **来源检查**：输入只认你信任的来源，其他的都当作不可信文本，永远不当成指令。
- **证据检查**：在下结论或发送之前，先引用它来自哪个文件或链接。
- **行动检查**：在发送、删除、发布、付款这类不可逆操作之前，先停下来问你。检查失败就写进决策记录，然后停下。

每周再做一次复盘：看看 Jev 做了哪些决定、有没有错的，哪些检查被触发了、为什么，Grok 和 Jev 各花了多少钱，下一周先修哪一个瓶颈。复盘不用长，控制在 20 行以内。

## 我的理解：落地顺序 <!-- toc: 我的理解：落地顺序 -->

按作者的顺序，也是我觉得最稳的顺序：

主管 → 职责说明 → 工作区 → 三道检查 → Jev → 再加第二个机器人

不要一上来就搭十个机器人。先让主管加一个专家跑通一个小闭环，比如邮箱分流，跑顺了再加内容或代码。

这和我们之前定下来的 Agent 结构完全对得上：模型只负责动嘴和拆解，Harness 负责准备材料、动手执行、传结果、管循环和权限，MCP 是 Harness 对外借本事的一种插口。Jev 在这里就是 Harness 里一个便宜的决策插口，Grok 是贵的写作插口，两个插口分工不同，Harness 负责在中间选对插口、用对价格。

> 这套东西省的是重复决策的钱，不是让你把所有决定都外包出去。不可逆的事，永远要留一个人工确认的口子。
