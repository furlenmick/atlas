# AX3600 代理链泄漏排查与 fail-closed 加固（定版）

> 定版状态：2026-10-29 DNS 定版、2026-10-23 fail-closed 结构已实施。
> 前置阅读：先完成《小米 AX3600 刷 OpenWrt 做旁路由完整教程》，本篇是在旁路由跑起来之后，把"不泄漏"和"出故障时不出包"这两件事做扎实。
> 红线：在 RackNerd 前置链建成、策略组切回住宅链、复测全绿之前，不在这条连接上登录 Claude。

## 当前链路状态（排查的起点）

- AX3600 的 WAN 是 192.168.31.110/24，分流方式为 TCP Redirect + UDP TProxy。
- DNS 走 Fake-IP，假地址段 198.18.0.0/16。
- 当前出口是机场机房节点，不是 Verizon 住宅链——所以这条链目前只适合一般用途，不能碰地区敏感账号。

## 步骤一：DNS 定版（2026-10-29 定版，不要再改）

1. 只保留国外 DoH 作为解析上游，不混用国内解析。
2. Fake-IP 保持开启。
3. dnsmasq 的上游唯一指向 `127.0.0.1#7874`（本机 Clash 的 DNS 监听），不要再加第二个上游。

验收：改完后用 browserleaks 重测。2026-10-29 实测结果干净（出口、DNS 均显示美国）。

## 步骤二：堵 STUN / WebRTC 泄漏口（2026-10-27 定版）

现象：Claude 的检测工具报告 DNS / WebRTC 可能泄漏，排查后定位到 STUN 流量绕过了代理。

处理：在分流规则里把目标端口 3478 和 5349（STUN 常用端口）改为 **REJECT**。

- 改完之后未再复发。
- 代价（已知、接受）：这台 Chrome Profile 开不了网页版 Meet / Zoom 这类 P2P 通话。开会时走 BE7200 主网，或换一个浏览器。

## 步骤三：fail-closed 结构加固（防"故障"，不防"主动切直连"）

为什么要做：大陆 IP 碰一次 Anthropic 就可能封号。而 OpenClash 核心停止或崩溃时，劫持规则会被清理、路由器 NAT 还在，桌面版在托盘后台的连接就会以真实 IP 自己撞上 Anthropic。节点或订阅挂掉只是连接失败，那是安全态；核心死了才是危险态。

做法（在 AX3600 防火墙里）：

1. 删掉 lan → wan 的区域转发。
2. 删掉 lan → wan6 的区域转发。
3. 结果是 Zones 表里 lan ⇒ REJECT：核心一死，192.168.2.x 网段一个包都出不了 WAN。

已知副作用（都可接受、且完全可逆）：

- ICMP ping 不再可用。
- 如果 2.x 网段访问主网段设备受影响，加两条放行规则：去 192.168.31.0/24、去 192.168.1.0/24。

操作纪律：

- 这套加固防的是核心故障，防不了人主动把模式切成直连。所以维护网络之前，先彻底退出 Claude 三端（桌面版、CLI、网页版）。
- 待办：保存应用后做一次冒烟测试，再停掉核心做一次断网验收，确认 2.x 网段确实出不了包。

## 踩坑记录

- **检测口径不一致**：2026-10-29 同一天，browserleaks 重测已经干净，但 Claude 的检测工具仍报 DNS / WebRTC 可能泄漏。此条未最终确认——以后复测时以两个工具交叉验证为准，不要只信一边。
- **STUN 端口 REJECT 是一把双刃剑**：堵住了泄漏，也堵掉了网页版视频会议的 P2P 通话。先想清楚哪台设备要开会，再决定规则加在哪个 Profile / 网段上。
- **真正的风险不是节点挂掉，是核心死掉**：节点故障 = 连不上（安全）；核心崩溃 + NAT 还在 = 真实 IP 裸奔（危险）。加固要针对后者。
