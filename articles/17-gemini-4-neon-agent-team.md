# Gemini 4 Neon：用一个 AI Agent 团队干活，而不是一个聊天窗口

## 问题出在哪：只当聊天窗口用 <!-- toc: 问题出在哪 -->

<!-- lead -->
作者开篇的判断是：Gemini 4 Neon 是当月最被低估的模型，不是因为它不够强，而是 99% 的人只用到了它大概三分之一的本事。

大多数人的用法是：打开一个聊天窗口，把需求整段贴进去，等它一次答完。这样用有三个毛病：

1. **上下文越攒越重**：一个窗口里既要理解需求、又要写代码、又要检查自己，上下文一路膨胀，越到后面越容易走偏。
2. **贵模型干便宜活**：写一行注释和做一次架构判断，按同一个价格结算。
3. **没人复核**：它说做完了，你只能信它，假完成混在真完成里，分不出来。

作者认为 Google 设计 Neon 的本意不是再造一个更强的单聊窗口，而是让它当一支队伍的队长：**一个模型家族一起干活**。这和我们之前记的 Grok Harness 笔记是同一个思路：模型只负责动嘴和拆解，外面的组织方式决定了最后能走多远。

## Neon 是一套模型家族 <!-- toc: Neon 是一套模型家族 -->

Neon 不是一个模型的名字，而是一家子，分工不同，价格也不同：

- **Neon Pro**：旗舰，当总协调和大脑，负责规划、复杂推理、写作和代码架构。
- **Flash**：快、便宜的执行者，适合量大、重复的活。
- **Deep Think / Deep Research**：深度研究和长推理，适合需要慢慢想的任务。
- **Nano Banana 2**：负责生成和编辑图片。
- 原文的团队示意图里还列了 Deep Research、Nano Banana 2、Omni L2 Flash、3.0 Flash TTS，说明这个家族还可以按需要再扩。

核心原则只有一条：**一个 Agent 只干一件事**。职责单一，上下文就小；上下文小，并行才跑得起来，成本也才算得清。反过来，一个 Agent 什么都干，上下文一上来，什么都干不好。

这和 Grok 那边的四层分工是能对上的：贵的只留在真正需要动脑的地方，便宜的去跑量大的执行，只不过这里的执行者是同一家族里不同档位的模型。

## 团队架构：一个总协调，加一群专职队员 <!-- toc: 团队架构 -->

![图 1 · Neon 团队架构：总协调在上，子 Agent 群在下](kbimg:gemini-neon-architecture.jpg)

上面是总协调，下面是一群子 Agent，原文给的队员名单大概是这样：

- **@coordinator（总协调）**：接需求、拆任务、按专长分派、收结果、验收。它只做分解、分配和验收，**自己不写代码**。
- **@api**：后端和接口。
- **@ui**：界面。
- **@verifier**：校验者，最后把关，下一节细说。
- **@tests**：测试。
- **@docs**：文档。
- **@tin**：轻量、快速的小任务。

这个架构解决的是单 Agent 的两个老毛病：上下文过载，和假完成。总协调不直接动手，就不会被执行细节拖进上下文；校验者最后单独检查一遍，做完了还是没做完，有一个人专门负责较真。

## 八个步骤：从拿到 Neon 到跑起第一支队伍 <!-- toc: 八个步骤 -->

### 步骤 1 · 先拿到 Neon

原文给了四条路：订阅 Google AI Pro（每月 19.99 美元）、用 Antigravity、走 Gemini API 的命令行工具、以及用 API 密钥直连的路子。Workspace 账号的用户要走 API 密钥那条路。先有入口，再谈组队。

![图 2 · 原文步骤截图](kbimg:gemini-neon-s01.jpg)

### 步骤 2 · 装好 Antigravity

Antigravity 是 Google 的 Agent 开发环境。装好后建一个工作区，把默认模型设成 Gemini 4 Neon Pro，再把项目结构和需要接的服务准备好。这是队伍的驻地，之后所有队员都在这里干活。

![图 3 · 原文步骤截图](kbimg:gemini-neon-s02.png)

### 步骤 3 · 建 @coordinator 总协调

给总协调写一份职责说明，大意是：把任务拆小、按专长分给队员、收回结果、验收通过再交给用户；自己绝不写代码。这一条是写死的，不是建议——总协调一旦开始自己动手，上下文和责任就全乱了。

![图 4 · 原文步骤截图](kbimg:gemini-neon-s03.jpg)

### 步骤 4 · 建子 Agent 群

给每个队员各写一份职责说明，各配各的模型和工具：后端、界面、测试、文档、轻任务，各归其位。配模型时按活的轻重来：协调和关键判断用 Pro，快速执行用 Flash。不要所有活都跑在最贵的旗舰上，那是烧钱最快的姿势。

![图 5 · 原文步骤截图](kbimg:gemini-neon-s04.jpg)

### 步骤 5 · 写 AGENTS.md

这一步在第 5 节单独细说。简单讲：AGENTS.md 是全队的共享规则文件，所有队员都按它办事。

![图 6 · 原文步骤截图](kbimg:gemini-neon-s05.jpg)

### 步骤 6 · 加 @verifier 校验者

每个任务最后都要过校验者这一关。这一关是作者眼里整套做法里最关键的一环，第 6 节细说。

![图 7 · 原文步骤截图](kbimg:gemini-neon-s06.jpg)

### 步骤 7 · 跑第一次 /swarm

用一条真实的任务命令启动队伍，比如给 HTTP 客户端加上指数退避重试。流程是：总协调拆解 → 队员并行执行 → 收回结果 → 校验者检查 → 交付。第一次不用大，就要一个完整闭环。

![图 8 · 原文步骤截图](kbimg:gemini-neon-s07.jpg)

### 步骤 8 · 扩到 T3 Code 这类多线程环境

同一套做法搬进 T3 Code 这样的多线程环境，用多线程并行队伍接更大的任务。原文举的例子是 Theo（t3dotgg）用 T3 Code 做并行实践的做法。先在小环境跑通，再扩规模，顺序别反了。

## 团队规则 AGENTS.md：写给全队看的同一份规矩 <!-- toc: 团队规则 AGENTS.md -->

AGENTS.md 是整个队伍共享的规则文件，原文强调了几条：

1. **总协调只做分解、分配和验收，绝不写代码**。
2. **每个子 Agent 一份工作、一个模型、一套工具**，职责写死，不串岗。
3. **不碰职责之外的文件**：每个队员只动自己那摊，出界就是事故。
4. **占位符和没做完的东西，绝不能当成做完了交上来**：没做完就写没做完，留空就写留空。

这份文件的作用和 Grok 笔记里的 Harness 规则是一回事：把规矩写在模型外面，让 Harness 和流程去管，而不是指望模型自己自觉。规矩越清楚，队伍越大越不乱。

## 校验者为什么最关键：防幻觉，也防假完成 <!-- toc: 校验者为什么最关键 -->

<!-- lead -->
作者把 @verifier 叫做整套做法里最关键的一步，理由很直接：没有校验者，Agent 说做完了就是做完了，你没有第二双眼睛。

校验者的做法是：把队员声称的结果，逐条对照代码和测试结果核查，引用行号和测试证据；核查不过的打回去；**没法核实的，就明确写「无法核实」，绝不能含糊放过**。

这一步同时防两种毛病：

- **幻觉**：模型编了一个看起来合理的答案，但代码里根本没有。
- **假完成**：任务只做了一半，占位符还在，汇报却写「已完成」。

和 Grok 笔记里最后由中立合并机器人统一落地的思路一样：写功能的人不负责验收，验收的人不写功能。两边分开，假完成才混不过去。

## 成本陷阱与评测陷阱：单价会骗人 <!-- toc: 成本陷阱与评测陷阱 -->

这是全文最值得细看的一节，数字都在这里。

### 先看单价

- **Neon Pro**：输入每百万 token 3 美元，输出 15 美元。
- **Hydrogen**：输入 1.50 美元，输出 7.50 美元。
- **Carbon**：限时价输入 2 美元、输出 10 美元，到 2026 年 11 月 30 日为止；从 2026 年 12 月 1 日起涨到输入 4 美元、输出 20 美元。

只看单价会得出「Pro 最贵、Carbon 最便宜」的结论，但作者提醒：单价是最会骗人的数字。

### 订阅和按量，差了一个数量级

原文给了一个反直觉的对比：同样一个 50M token 的单 Agent 任务，走 API 按量付费大约要 **900 美元**，而在每月 19.99 美元的 Google AI Pro 订阅里，同样用量大约只要 **20 美元**。用量越大，订阅和按量的差距越大。先算自己一个月的用量，再选付费方式，别只看单价。

```bill

```

### 队伍越并行，烧得越快

组队不是免费的：子 Agent 每人一份自己的上下文、自己的一份 token 消耗，队伍整体的用量大约是单个 Agent 的 **4 到 5 倍**。并行换来的是速度和分工，不是省钱。扩队伍之前，先想清楚省下的时间值不值这几倍的用量。

### 评测分数也会骗人

SimpleBench 的提醒是：同一个模型，在不同评测框架下能跑出 **12.8% 到 39.0%** 的分数，差的是框架，不是模型。看评测先看框架，再看分数。

还有一个容易忽略的成本项：输出长度。Neon 平均每次输出约 **2,385 个 token**，而 Opus 5.5 约 **575 个**。输出越长，输出 token 的账单越长。原文还引用了一次完整运行的对比：**7.99 美元对 2.74 美元**——单价、用量、输出长度、并行消耗，四项一起算才是真实成本，只看其中一项都会算错。

## 最小可用形态与落地顺序：一个晚上搭起来 <!-- toc: 最小可用形态与落地顺序 -->

作者的结论是：Neon 本身不是魔法，优势来自队伍、规则和校验这三件套加在一起。最小可用形态不用大：

1. 一个总协调 @coordinator。
2. 几个专职子 Agent（后端、界面、测试、文档，先按需配）。
3. 一个严格的 @verifier，最后把关。
4. 一份写清楚的 AGENTS.md。

然后拿一个真实任务跑通一次完整闭环，跑顺了再扩规模。按作者的说法，搭起这套东西大约只要一个晚上的时间。

落地顺序和我们之前记的 Grok 笔记是一致的：先让总协调加一两个专家跑通一个小闭环，规矩和校验先立起来，再加人、再扩规模。顺序反了——先搭十个队员、再补规则——最后一定是返工。

> 模型是队员，队伍、规则和校验才是战斗力。先把一个真实任务完整跑通，再谈规模。
